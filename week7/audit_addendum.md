These clarifications were prepared with a chat assistant after the original

## Actual prompt and input contract

The English template is `prompts/rerank.txt`. It is a proposed fixed template for
the later experiment; it has not been executed or tokenizer-tested. Substitute
JSON into its two placeholders. Freeze the exact bytes before development.

Create one per-user alias map over the union of the history and candidate assets.
Assign opaque labels from a pseudorandom permutation, with seed 2025 and a stable
user order recorded in the protocol. A shared asset must use the same alias in
both sections. Keep this map fixed across A and B. Only candidate aliases may be
returned. The adapter maps `ranked_aliases` back to the starter's `ranked_ids` and
validates ten distinct IDs inside the frozen pool before writing a response.
Administrative fields such as user ID and protocol hash stay outside the model.

Preserve the starter baselines and evaluator. The later implementation must use
the frozen union pool in both prompt export and response validation: leaving
validation on the default CBF-only candidates would reject valid union-pool IDs.
Save the actual pools, alias maps, source-code revision, prompt hash, and model
revision alongside the starter protocol. Its existing protocol hash does not
by itself identify this added candidate policy or prompt.

Source-ranking ties and pool-fill ties use ISIN. Final RRF score ties use the
same opaque aliases as the model. Main A uses canonical alias order; main B
permutes candidate rows with seed 2026. The history order stays unchanged.

The classical pipeline uses complete past histories. The LLM sees at most the
20 most recent distinct eligible past-buy assets, with counts computed from
all their pre-cutoff buys. Count, recency, source ranks, and aliases are derived
at the cutoff; none is an LLM-estimated preference. This is a different
representation of the same underlying fields, not an identical feature vector.
The history cap can itself limit the LLM and must be acknowledged.

Missing, duplicate, out-of-pool, truncated, oversized-context, and invalid-JSON
outputs use RRF for that user and are counted by reason. Do not truncate input
silently, invent IDs, or remove users. The fallback adapter must be implemented
explicitly; the starter's ordinary invalid-response fallback is CBF.

## Ground truth and comparison

Future eligible Buy IDs are the only relevance labels. An LLM is not used as a
judge. Sells are not interpreted as dislikes. The pool and labels are identical
for RRF and LLM within each evaluated user. The RRF row is the no-LLM ablation.

Candidate recall and ordering quality answer different questions. For example,
with two relevant items and only one inside the pool, even a hit at rank 1 has
maximum nDCG equal to `1 / (1 + 1/log2(3)) = 0.613147...`, below one. This is an
analytical example, not a result on a FAR-Trans user. The saved calculation is in
`results/design_checks.json`, generated by `eval/check_design.py`.

## Budget feasibility before a full run

The total remains 300 calls: 100 development, 100 main A, and 100 main B. A
one-hour cap permits at most 12 seconds per call even if setup takes no time.
No throughput has been measured, so the cap is not proof of feasibility.

Time model loading, preprocessing, and the first ten development calls. Keep
those calls as part of the development pass; do not add extra calls. Extrapolate
to all remaining calls. If the projected total cannot fit the cap or US$5 rental
limit, report the plan as infeasible under that budget before the main test.
Do not quietly change the model, cohort, prompt, or budget after seeing labels.

The 100-user June setup is a teaching pilot, not the final project protocol.
The common official cohort, item scope, and split still need confirmation.
Report the number of users with nonempty future truth; do not assume the
reference README count is the result of a run that has not happened.
